# ISO/IEC 27001 y 27002 · Codificación segura y perfiles de acceso en Abarrato

> **Para usar con IA:** adjunta este archivo y pide: *"Revisa este código Java/SQL contra el control 8.28 (codificación segura) y los controles de acceso 5.15–5.18 y 8.2 descritos aquí. Lista los incumplimientos con archivo y línea."*

## Qué es cada norma

| Norma | Qué es | Cómo se usa en Abarrato |
|---|---|---|
| **ISO/IEC 27001:2022** | Requisitos de un **sistema de gestión de seguridad de la información (SGSI)**: evaluar riesgos, elegir controles y mejorar continuamente. Es la que se certifica. Su Anexo A lista 93 controles. | El "qué": identificar riesgos y decidir qué controles aplicar (ver la tabla de riesgos abajo). |
| **ISO/IEC 27002:2022** | **Guía de implementación** de esos 93 controles, ordenados en 4 temas: organizacionales (5), de personas (6), físicos (7) y tecnológicos (8). | El "cómo": buenas prácticas concretas de código y de cuentas. |

La codificación segura no es un capítulo de 27001. Es el **control 8.28 "Codificación segura"**, nuevo en la edición 2022, que 27001 exige en su Anexo A y 27002 explica. Los perfiles de cuentas y de bases de datos corresponden a los controles de acceso **5.15 a 5.18, 8.2, 8.3 y 8.5**.

## Parte 1 · Buenas prácticas de codificación (control 8.28 y relacionados)

| Práctica | Control | Cómo se aplica en Abarrato | Archivo |
|---|---|---|---|
| Validar toda entrada en el servidor, aunque el cliente ya valide | 8.28 | Largo y contenido de la búsqueda, tamaño del carrito, claves de producto | `ControladorPrecios.validarConsulta`, `ServicioPrecios` |
| Consultas parametrizadas; nunca concatenar SQL con datos del usuario | 8.28 | `JdbcTemplate` con `?`; el patrón LIKE escapa `%`, `_` y `\` | `RepositorioPrecios.buscarCatalogo` |
| Errores que no revelan detalles internos | 8.28 | Manejador central, sin trazas ni SQL; `include-stacktrace: never` | `ManejadorErrores`, `application.yml` |
| Sin secretos en el código ni en el repositorio | 8.28, 5.17 | Variables de entorno en Cloud Run; `.gitignore` bloquea `.env` | `application.yml`, `.gitignore` |
| Comparar secretos en tiempo constante | 8.5 | Token de la tarea diaria con `MessageDigest.isEqual` | `TareaDiaria` |
| No confiar en encabezados del cliente para registros | 8.15, 8.28 | La IP de `X-Forwarded-For` se valida antes de escribirla en el log | `LimitePeticiones.pareceIp` |
| Mínimo privilegio en tiempo de ejecución | 8.2 | El contenedor corre con un usuario sin permisos de administrador | `backend/Dockerfile` |
| Integridad de datos también en la base | 8.28 | Restricciones `CHECK` iguales a las reglas de `ObservacionPrecio` | `V10__restricciones_integridad.sql` |
| Pruebas de seguridad en el desarrollo | 8.29 | `SeguridadTest`, `ContratoApiTest`, `CajaGrisTest` (inyección SQL) | `backend/src/test` |
| Separar desarrollo y producción | 8.31 | Base local o rama de Neon para pruebas; producción solo en Cloud Run | `docs/MANUAL.md` |
| Control de cambios | 8.32 | Migraciones Flyway numeradas; registro de decisiones; CI | `db/migration`, `docs/DECISIONES.md` |
| Revisar dependencias | 8.8, 8.28 | Spring Boot 3.5 terminó su soporte gratuito en junio de 2026: pendiente pasar a 4.x | `pom.xml` (ver D12) |

### Reglas cortas para el equipo

1. Todo dato que viene de afuera (app, tienda, encabezado) es sospechoso hasta validarlo.
2. SQL solo con parámetros `?`. Si se usa LIKE, escapar los comodines.
3. Un error al usuario: mensaje claro y nada más. El detalle va al log.
4. Ninguna clave en el código, en un commit ni en el chat. Si se expone una, se cambia.
5. Cada cambio de base de datos es una migración nueva; nunca se edita una ya aplicada.
6. Cada regla de negocio nueva lleva su prueba.

## Parte 2 · Perfilamiento de cuentas y bases de datos

### Controles que aplican

| Control | Qué pide (en palabras simples) | Aplicación |
|---|---|---|
| **5.15 Control de acceso** | Reglas escritas de quién puede acceder a qué | Tabla de perfiles de abajo |
| **5.16 Gestión de identidades** | Cada persona o sistema con su propia cuenta; nada de cuentas compartidas | Una cuenta por función: dueño, servidor y lectura |
| **5.17 Información de autenticación** | Contraseñas fuertes, entregadas de forma segura y cambiadas si se exponen | Neon genera las claves; van directo a Cloud Run; el token se rotó |
| **5.18 Derechos de acceso** | Dar, revisar y quitar permisos de forma controlada | `db/roles.sql` deja escritos los permisos y termina con una consulta de verificación |
| **8.2 Derechos de acceso privilegiado** | Las cuentas con poder total se usan lo menos posible | `neondb_owner` solo para Flyway; el servidor usa `abarrato_app` |
| **8.3 Restricción de acceso a la información** | Cada cuenta ve solo lo necesario | `abarrato_lectura` solo puede leer; `abarrato_app` no puede borrar |
| **8.5 Autenticación segura** | Mecanismos robustos y sin filtrar información | Conexión a Neon con SSL (`sslmode=require`); token comparado en tiempo constante |

### Perfiles definidos

| Perfil | Quién lo usa | Puede | No puede | Límites |
|---|---|---|---|---|
| `neondb_owner` | Flyway, al desplegar | Crear y modificar tablas | — (es el dueño) | Su clave solo en `ABARRATO_MIGRATION_PASSWORD` |
| `abarrato_app` | El servidor en Cloud Run | `SELECT`, `INSERT`, `UPDATE` en `observaciones_precio` | `DELETE`, `DROP`, `ALTER`, crear tablas | 10 conexiones, consultas de 30 s como máximo |
| `abarrato_lectura` | Reportes, revisión del profesor | `SELECT` | Cualquier escritura (sesión de solo lectura) | 3 conexiones, consultas de 15 s |
| Cloud Scheduler | Tarea diaria | Llamar `POST /actualizar` con el token | Nada más | Token largo generado al azar |
| Integrantes del equipo | Consola de Google Cloud y de Neon | Desplegar y administrar | — | Cuenta personal con verificación en dos pasos |

**Cómo aplicarlo:** sigue las instrucciones al comienzo de [`db/roles.sql`](../../db/roles.sql).

**Revisión periódica (5.18):** cada vez que alguien deje el equipo, o una vez por semestre, ejecutar la consulta final de `roles.sql` y quitar lo que sobre.

### Riesgos y controles (enfoque 27001)

| Riesgo | Probabilidad | Impacto | Control aplicado |
|---|---|---|---|
| Se filtra la clave del servidor | Media | Medio: pueden escribir precios falsos, pero no borrar | Perfil `abarrato_app` sin `DELETE` ni `DROP` (8.2, 8.3) |
| Un script satura la API | Alta | Medio: costo y bloqueo de las tiendas | Límite de peticiones (8.6, 8.16) |
| Alguien lanza la tarea diaria sin permiso | Baja | Medio | Token y rotación (5.17) |
| Inyección SQL | Baja | Alto | Consultas parametrizadas y pruebas de caja gris (8.28) |
| Dependencia vulnerable | Media | Alto | Actualizar Spring Boot; CI (8.8) |
